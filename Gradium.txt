1. PROJECT OVERVIEW
What problem does this solve? Traditional power grids are monolithic, centralized, and brittle. As distributed energy resources (DERs)—like residential solar panels and home batteries—proliferate, the legacy grid struggles to manage bidirectional energy flows efficiently. Currently, prosumers (consumers who also produce) sell surplus energy back to utilities at wholesale pennies, while neighbors buy it back at retail premiums. Furthermore, unregulated decentralized peer-to-peer (P2P) trading introduces physical grid instability (e.g., synchronized trading causing localized brownouts) and severe privacy risks (public ledgers revealing physical home occupancy based on energy usage).

Gridium solves the "Decentralized Energy Trilemma" by providing a stable, private, and automated P2P microgrid economy.

Why is this problem important in real-world context? The transition to renewable energy requires localized microgrids to prevent systemic failures (like the Texas grid crisis). However, physical infrastructure cannot handle the volatility of free-market trading without intelligent orchestration. Ensuring grid stability while maintaining economic fairness for prosumers is critical for the next generation of physical infrastructure.

Who are the users?

Residential Prosumers: Homeowners with solar arrays and batteries who want to maximize their ROI by selling surplus energy directly to neighbors.
Energy Consumers: Residents seeking cheaper, locally sourced renewable energy.
Microgrid Operators & Municipalities: Entities looking to deploy resilient, self-sustaining community grids without massive capital expenditure in centralized physical infrastructure.
What makes this project unique? Gridium operates at the intersection of AI, cryptography, and decentralized finance (DePIN). It utilizes an Automated Market Maker (AMM) for instant energy liquidity, governed dynamically by a Deep Deterministic Policy Gradient (DDPG) reinforcement learning agent acting as an autonomous grid operator. Finally, it secures physical location and usage privacy via zk-SNARKs (Groth16), ensuring trades are mathematically verified on-chain without exposing raw telemetry data.

2. SYSTEM ARCHITECTURE
The Gridium Protocol is a highly decentralized, microservices-oriented distributed system.

System Flow: Sensor Data (Simulated) → Fast Data Ingestion (Gateway) → AI Physics Engine (RL Agent) → Cryptographic Proof Generation (ZK) → Blockchain Settlement (EVM) → Real-time Visualization (WebSocket/React)

Component Breakdown:

Frontend (Command Center): React 18, TypeScript, Vite. Utilizes React Three Fiber for real-time 3D topology visualization and Zustand for high-frequency state management.
Gateway (Ingestion & Routing): Node.js, Express, Socket.io. Acts as the nerve center. It bridges the Python physics engine to the web clients and handles computationally heavy off-chain tasks like zk-proof generation using snarkjs.
AI Engine (Physics & Intelligence): Python, FastAPI, PyTorch. Contains the AegisEnv (a custom Gymnasium environment simulating 15 nodes, battery states, and grid load) and the DDPG Agent (ddpg_agent.py) which calculates optimal swap fees in real-time.
Blockchain Layer: EVM-compatible smart contracts (Solidity). Includes the AegisAMM (handling USDC/Energy token swaps using the $x \cdot y = k$ invariant) and the SurplusVerifier (for on-chain Groth16 proof validation).
Cryptographic Layer: Circuits compiled via circom, outputting .wasm and .zkey artifacts for client-side/gateway-side proof generation.
Component Interactions:

AI Engine ticks every 500ms, running the physics simulation and DDPG inference.
Gateway polls the AI Engine via REST (/tick) and broadcasts the state via WebSockets to connected Frontends.
When a node initiates a trade, the Frontend requests a proof from the Gateway (/api/generate-proof).
The Gateway computes the Groth16 proof based on the node's generation/load delta and returns the payload.
The Frontend submits this proof to the Smart Contract via Ethers.js.
The Blockchain verifies the ZK proof and settles the trade, updating the AMM reserves.
3. DATA FLOW PIPELINE
Data Ingestion & Generation: Data originates in the Python AegisEnv. It generates synthetic but highly realistic telemetry for 15 nodes, including solar generation curves, residential load profiles, and battery State of Charge (SoC). Noise and jitter algorithms simulate real-world sensor inaccuracies.

Processing & Transformations:

Physics Step: AegisEnv calculates grid imbalance (Total Generation - Total Load).
State Vectorization: Telemetry is normalized into a state vector (prices, reserves, imbalance, SoC) conforming to the Observation Space expected by the neural network.
Action Transformation: The DDPG output (a continuous float between -1 and 1) is scaled to a realistic swap fee percentage (e.g., 0.1% to 5.0%).
Storage & Persistence: Currently, state is ephemeral, held in memory in the Python Engine and propagated via Zustand in the Frontend. Historical OHLC (Open, High, Low, Close) candlestick data is aggregated in a sliding window within the React client for visualization.

Inference Flow:

At tick $t$, Python Engine builds Observation State $S_t$.
DDPG Actor network processes $S_t$ and outputs Action $A_t$ (Swap Fee).
Physics engine applies $A_t$, observes Reward $R_t$ and Next State $S_{t+1}$.
Tuple $(S_t, A_t, R_t, S_{t+1})$ is stored in the Replay Buffer for asynchronous training.
4. MACHINE LEARNING / AI LOGIC
Model Used: Deep Deterministic Policy Gradient (DDPG). An actor-critic, model-free algorithm operating over continuous action spaces.

Why this model? Discrete action spaces (like DQN) are insufficient for financial fee parameters, which require granular, continuous floating-point adjustments to prevent market shock. DDPG handles continuous controls efficiently, making it ideal for "steering" a physical grid via economic incentives.

Training Regime:

Environment: Custom gymnasium.Env simulating Ohm's law, battery degradation, and AMM bonding curves.
Reward Function: A highly engineered composite reward. It penalizes grid imbalance heavily (squared error) while rewarding AMM liquidity depth and maintaining battery SoCs between 20% and 80%.
Exploration: Ornstein-Uhlenbeck (OU) noise process added to action outputs during training to encourage exploration of the state space.
Target Networks: Polyak averaging (soft updates) is used for target networks to provide stable Q-value targets.
Inputs (State): [grid_load, generation, grid_imbalance, energy_reserve, stable_reserve, current_price, battery_soc] Outputs (Action): [swap_fee_modifier]

Limitations & Improvements:

Limitation: DDPG can be sample inefficient and highly sensitive to hyperparameters.
Improvement: Upgrade to Soft Actor-Critic (SAC) for entropy maximization, leading to more robust policies in highly stochastic physical environments. Implement recurrent layers (LSTM/GRU) to give the agent memory of temporal trends (e.g., anticipating evening peak demand).

6. PERFORMANCE & SCALABILITY
Current Load Profile: The system processes state at 2 Hz (500ms intervals). The Node.js gateway handles fan-out broadcasting to WebSocket clients.

Bottlenecks:

Synchronous AI Ticks: Running the PyTorch inference synchronously in the FastAPI event loop blocks requests.
ZK Proof Generation: Generating Groth16 proofs in Node.js is CPU-intensive and halts the v8 event loop, potentially lagging WebSocket broadcasts under heavy load.
Scalability Roadmap:

Decouple Prediction from Simulation: Move PyTorch inference to a dedicated microservice using TorchServe or ONNX Runtime. Send requests via gRPC.
Scale Gateway via Pub/Sub: Utilize Redis Pub/Sub backplane. The Python engine publishes states to Redis; horizontally scaled Node.js Gateway instances subscribe and broadcast to their respective connected clients.
WASM/WebWorker ZK: Push the ZK proof generation entirely to the client-side browser using Web Workers, freeing up the backend compute entirely.
7. FAILURE MODES
Model Degradation (Concept Drift):
Failure: Changing seasonal weather patterns render the trained policy obsolete; the agent sets fees too low during high load, crashing the grid.
Detection: Monitor the rolling average of the RL Reward signal. If it drops below a defined threshold, alert for retraining.
WebSocket Avalanche:
Failure: Render backend restarts; thousands of frontends attempt to reconnect simultaneously, causing a thundering herd DDoS.
Mitigation: Implemented exponential backoff and jitter in the Socket.io client reconnect logic.
Malicious Actor Data Injection:
Failure: A compromised smart meter reports false high solar generation to drain USDC from the AMM.
Mitigation: The zk-SNARK circuit limits maximum provable bounds. The system also includes a Slash Registry fallback; if statistical distribution anomalies are detected on-chain, the node's stake is slashed.
8. MONITORING & OBSERVABILITY
System Metrics (Datadog / Prometheus + Grafana):

Gateway: WebSocket concurrent connections, message latency, event loop lag.
AI Engine: Tick loop execution time (must remain < 500ms), endpoint response times.
ML-Specific Observability (Arize AI / MLflow):

Feature Drift: Monitor distribution shifts in grid_load vs historical baselines.
Action Distribution: Track the frequency of extreme fee adjustments. High frequency indicates the agent is struggling to maintain control.
Reward Trajectory: Real-time dashboarding of the episodic reward scalar.
9. SECURITY & RELIABILITY
Zero-Knowledge Privacy: Crucially, physical location and raw wattage data never touch the public internet or blockchain. Only cryptographically sound proofs of mathematical relationships (Surplus > 0) are broadcasted.
Smart Contract Security: The AMM relies on the audited $x \cdot y = k$ invariant. Staking mechanisms ensure economic disincentives for attacks (Byzantine fault tolerance via slashed stakes).
Rate Limiting: Gateway API endpoints (/execute-trade, /api/generate-proof) must implement IP-based rate limiting to prevent resource exhaustion attacks.
10. REAL-WORLD IMPACT
Gridium attacks the trillion-dollar energy sector by eliminating the monopolistic utility middleman. Through the DePIN (Decentralized Physical Infrastructure Networks) framework, it allows neighborhoods to fund, deploy, and profit from their own localized energy infrastructure. It solves the critical bottleneck of P2P energy—grid stability—by replacing static SLAs with an AI that reacts to physical reality in milliseconds, creating a more resilient, equitable, and sustainable local grid.
