Overview

KrushiMitra ("friend of the farmer" in Odia) addresses a critical gap in Indian agriculture — most crop yield prediction tools are designed for large-scale commercial farms or require expensive sensors. This platform brings accessible, data-driven crop predictions to smallholder farmers in Odisha using nothing more than a phone and basic seasonal knowledge.

Farmers enter soil type, rainfall, season, district, and crop type. Within a second, a trained ML model returns a predicted yield in tonnes per acre — along with a comparison to regional averages and actionable recommendations.

Interaction Flow

How It Works — Step by Step

01

Farmer Fills Input Form

The farmer selects their district, soil type (Clay Loam, Sandy, Black, Red), crop (Rice, Wheat, Maize, etc.), expected rainfall range, and growing season (Kharif / Rabi / Zaid). Designed for low-literacy environments with visual icons.

5 features · dropdown-first UX · works on 2G
02

Feature Engineering on the Backend

Flask receives the form POST, encodes categorical features (soil type → numerical), normalises rainfall values, and constructs the feature vector expected by the trained model.

One-hot encoding · MinMaxScaler · feature vector [5 dims]
03

Random Forest Prediction

The serialised Random Forest model (trained on 6 years of Odisha Agricultural Department records) predicts yield in tonnes/acre. The model ensemble of 100 decision trees outputs both a point prediction and a confidence interval.

RandomForestRegressor · 100 estimators · R² = 0.87
04

Contextualised Output

The prediction is enriched with district-level average yield data, a percentage deviation, and a recommendation (e.g., "12% above district average — consider intercropping with legumes"). All returned as a clean JSON response.

{ yield: 4.2, avg: 3.7, delta: "+12%", tips: [...] }
Engineering Problems Solved

Challenges & Solutions

Problem

Sparse and inconsistent agricultural data

Odisha crop yield records had missing values, inconsistent units (quintal vs kg vs tonne), and varying district names across years, making raw data unusable.

Solution

Custom ETL pipeline + data normalisation

Built a pandas-based ETL pipeline that standardised units, mapped district name variants, and imputed missing values using district-level medians. Increased usable records by 40%.

Problem

Low smartphone penetration in target user base

Many Odisha farmers use entry-level Android devices with slow internet. A typical React SPA would be unusable on these devices.

Solution

Progressively enhanced mobile-first frontend

Built with vanilla HTML/CSS/JS — zero framework dependencies, total JS payload under 12kb. Form state preserved in localStorage so network drops don't lose input.

Problem

Model overfitting on district-level data

Initial models trained per-district overfitted to small sample sizes and generalised poorly to unseen seasons.

Solution

Unified model with district as a feature

Switched to a single statewide model with district encoded as a categorical feature, using cross-validation across years. R² improved from 0.61 to 0.87.
